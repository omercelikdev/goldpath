## GP0405 — the consume seam (a WARNING, and TreatWarningsAsErrors makes it a build break)

The other half of preview.7's publish seam (ADR-0013): a handler names no bus type. The
analyzer flags `IConsumer<T>` implementations in application code — Warning from this
train, and the generated apps build with warnings as errors, so the swap is the one edit
that can go red. It is mechanical and it changes NO queue name (`OrderPlacedHandler` and
`OrderPlacedConsumer` both drain `order-placed`):

```csharp
// before                                                      // after

public class OrderPlacedConsumer(OrdersDbContext db)            public class OrderPlacedHandler(OrdersDbContext db)
    : IConsumer<OrderPlaced>                                        : IIntegrationEventHandler<OrderPlaced>
{                                                               {
    public async Task Consume(ConsumeContext<OrderPlaced> ctx)      public async Task HandleAsync(OrderPlaced e, IntegrationEventContext ctx, CancellationToken ct)
    {                                                               {
        var order = await db.Orders.FindAsync(                          var order = await db.Orders.FindAsync(
            [ctx.Message.OrderId], ctx.CancellationToken);                  [e.OrderId], ct);
        ...                                                             ...

bus.AddConsumer<OrderPlacedConsumer>();                         bus.AddGoldpathHandler<OrderPlaced, OrderPlacedHandler>();
```

`IntegrationEventContext` carries what `ConsumeContext` used to: `MessageId`,
`CorrelationId`, `Tenant`, `RetryAttempt`, `Headers`. A consumer that genuinely needs the
library's pipeline (a saga, a request client) keeps `IConsumer<T>` with a written
`#pragma warning disable GP0405` justification (ADR-0005). Application projects that
referenced `MassTransit` only for the consumer contract reference `Goldpath.Messaging`
instead (the clean-architecture template's Application project does so now).

## GP1901 — an approval ladder that stops (an ERROR, approvals adopters only)

New on this train, and the only rule here that is an Error. `Rung(role, upToInclusive, …)`
bounds a rung; `TopRung(role, …)` is the one that covers everything above it. A ladder
built only from bounded rungs routes the largest amounts to its last CEILING — the rung
that was supposed to stop them. If your ladder ends in a `Rung`, it needs a `TopRung`:

```csharp
// before                                          // after
approvals.AddLadder("credit-limit", l => l         approvals.AddLadder("credit-limit", l => l
    .Rung("expert", 1_000_000m, hours8)                .Rung("expert", 1_000_000m, hours8)
    .Rung("manager", 5_000_000m, hours8, 2));          .Rung("manager", 5_000_000m, hours8, 2)
                                                       .TopRung("general-manager", hours24));
```

The rule reads only a configure lambda written inline; a ladder built in a method group is
not flagged, because the analyzer reports what it can see.

## Three more new rules, all Warnings

- **GP1902** — `AddGoldpathApprovals` with no `AddGoldpathApprovalsJobs()`. Every rung's
  `TimeSpan` is enforced by the scheduled sweep, not by the engine's read path: without it
  the deadlines are decoration and an unattended request waits at the rung it reached.
- **GP2101** — a file rail with no `ValidateRow`. Every parsed row is applied, so the
  quarantine is empty by construction and an empty quarantine reads as a clean rail.
- **GP2102** — `AddGoldpathFileExchange` with no `AddRail`. Ledger tables and a File rails
  screen over a module that can never ingest a file.

Generated apps build with warnings as errors, so these three are build breaks there too.
Each has a written fix above; suppressing one needs a justification (ADR-0005).

## FileExchange — one migration (`[schema]`)

`GoldpathFileQuarantine.QuarantinedAt` and `GoldpathFileArchive.ArchivedAt` join the
ledger model (the admin surface reads the age of a quarantined row and the archive time
of a file). Adopters on the EF ledger: `goldpath db add FileExchangeAdmin` and commit the
migration; both columns are additive. Then `app.MapGoldpathFileExchangeAdmin()` next to
the other admin surfaces (behind the auth floor, or `exposeUnsecured: true` as the visible
opt-out) — the console discovers it and shows "File rails".

## `goldpath add worker --trigger jobs` now REQUIRES a jobs rider on the solution

The in-solution fleet shares the app database's jobs tables, which the Api's context
owns; without a rider (archival/bulk/notification/campaign/approvals/fileexchange) it
booted against nothing. The verb refuses in words and names the alternatives. A worker
added to an authed solution is now authed, and it composes the solution's cross-cutting
features on its own context — nothing to declare, the manifest already says it.

## Additive, worth knowing

- The CLI closed four defects an adopter could hit on day one: the wizard offered a module
  the template cannot take (`outbox`), `goldpath add feature approvals` left the console's
  Approvals rail over an unmapped endpoint, `goldpath new service|gateway` silently
  swallowed flags like `--db`, and the usage text listed thirteen of the fourteen names
  `add feature` accepts. If you generated an app with an earlier preview and its Approvals
  panel showed nothing, map `app.MapGoldpathApprovalsAdmin(...)` yourself or re-run the
  recipe on this train.

- `Goldpath.ServiceDefaults` now exports the `Microsoft.EntityFrameworkCore` and `Npgsql`
  meters (the Data ops board reads them).
- `Goldpath.Messaging`: the publish filter now finds the correlation tag on the REQUEST
  activity (it was one child activity too low before, so the header was never stamped
  from inside a real request). Consumers that read `X-Goldpath-Correlation` start seeing it.
- Worker template: `--auth` and `--features` (see the template README); standalone
  workers on SQL Server now set the jobs store provider.
